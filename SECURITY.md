# Security policy

## Supported versions

Legion is young. Only the latest release on the default branch receives security fixes.

## Reporting a vulnerability

Please do not open a public issue for a security problem. Use GitHub's private vulnerability reporting instead: open the **Security** tab of this repository and choose **Report a vulnerability**. Include what you found, how to reproduce it, and the impact you expect. You can expect an acknowledgement within a few days.

## Threat model

Legion is a personal, local tool. It is not designed to be exposed to a network or shared between users.

- **Local-only binding.** Legion Core listens on `127.0.0.1` only. Do not proxy it to other machines.
- **Two secrets.** The MCP token in `config.json` lets Claude Code and Cowork run and read agents; it cannot approve, accept notes, change settings or change BSV policy (the one BSV thing it can do is Freeze, which only stops things). The admin secret exists only in memory while the Legion app is open. This stops a bot with a Bash tool from reading a file and approving its own request. It does NOT stop a process running as your Windows user from reading Legion's memory, editing its installed files, or talking directly to your BSV wallet on 127.0.0.1:3321. Only a VM or a separate OS account stops that. Every BSV spend is still confirmed in your wallet.
  - The **MCP token** (`authToken` in `config.json`, mode 0600) is accepted on `/mcp` and on a short client list only: `GET /api/state`, `/api/agents`, `/api/catalog`, `/api/tasks/:id` (and `/wait`), `POST /api/tasks`, `POST /api/tasks/:id/cancel`, and the event stream `GET /api/events`, which also accepts `?token=` because browsers cannot set headers on `EventSource`. Treat it like a password: anyone with it can run your agents, but only under the `ask` ceiling below.
  - The **admin secret** is made fresh by the Electron app each time it starts its core (32 random bytes, 64 hex characters; a core ignores any secret shorter than 32 characters and stays admin-closed), handed to that core over its stdin pipe, and kept in memory: never in an environment variable, argument, file or log, and never in `/health` (which only says `admin: true` or `false`; asked with a random nonce it answers HMAC(secret, nonce), which is how the app checks that the core it is about to trust really holds the secret, instead of trusting a pid). The app window sends it as `X-Legion-Admin` (also on its event stream, which it reads with `fetch`). Every other route, including every `/api/kg/*` route (reads too), rooms, BSV, settings, agent edits, approvals, VM routes, config, doctor and any path Legion does not know, needs it. The gate runs before routing, so an unknown path answers 403, not 404. The secret is compared in constant time.
  - A core started without the app (for example by the MCP stdio bridge for Cowork) has no admin secret, so its admin routes are closed to everyone (`403 admin_unavailable: open the Legion app`). When you open the app it stops an idle core of that kind and starts its own; if that core is busy it asks first. The app chooses the port once, starts its core on exactly that port and keeps using it: editing `port` in `config.json` afterwards does not redirect the window or the secret. The dev UI served with `?token=` is read-only for the same reason. Consequence for Cowork users: with only a headless core running, a task a client starts (or a peer such a task wakes) on an agent that needs approval waits 10 minutes for a card nobody can answer, then is denied with a message to open the Legion app.
  - **Replacing a foreign core is checked twice.** `/health` names a pid, but that is only a claim by whatever answers on the port. Before the app stops a core it did not start, it asks the operating system who owns the listener on that port (`netstat -ano` on Windows, `lsof` or `ss` elsewhere) and kills the claimed pid only if it is that process. If the pid does not own the port, or the lookup fails, the core is treated as blocked: the secret is withheld, nothing is killed and you are told to stop it yourself. The app starts its own core in a process group (Windows: `taskkill /T /F`) and stops the whole tree, so a `node` wrapper set in `LEGION_NODE` leaves no orphan core behind.
  - **Port squatting is a denial of service, and it sees the MCP token.** Another local process can take the port before the app starts. It cannot get the admin secret (it never answers the HMAC challenge) and cannot make the app kill an unrelated process; but Legion will not run until you stop it. In the blocked and "Later" cases the window keeps talking to whatever is on the port named in `config.json` with the MCP-class token only (never the admin secret), so a squatter learns that token and can read what the token reaches. This is why the token is a password and why admin routes are not behind it.
Under the cap a run also cannot write working memory (`kg_wm_set` is refused), and every private note it writes is stored as untrusted (its shared notes wait in the Inbox): that text is not shown in a later briefing, so something an MCP client (or a web page it fed to the bot) planted cannot reach the system prompt of the next run you start from the app. Starting a task from the app window itself is the only way to get an unrestricted run.
  - **`legion_vm` over `/mcp` has no Legion card.** The `legion_vm` tool (status, start, stop, `exec`, `desktop`) acts as the MCP client, not as an agent run, so it is not under the approval ceiling: a holder of the MCP token can run a shell command in a VM-enabled agent's boat.dev VM, or fetch its desktop URL, without a card. The gate for it is the MCP client's own tool-permission prompt (Claude Code and Cowork ask before calling a tool) and the secrecy of the token. Do not put anything in a VM that the token's holder must not reach; the VM is the isolation boundary, and the token is a password to it.
  - **Room text is reachable with the token.** The event stream hides `room.*`, `comms.*` and `settings.*` from a token-only client, but a woken bot's task messages (`GET /api/tasks/:id`, `/wait`, `legion_status`) legitimately contain the room text it was woken with, so a token holder who can start or find a task can read that text. Treat room contents as readable by anyone holding the MCP token.
- **Bots cannot make rooms on their own.** `room_create`, `room_add_member` and `room_remove_member` each wait for a card that only the Legion app can answer (the MCP token cannot approve), whatever the agent's approval mode; a decline, silence for 10 minutes or a cancelled task changes nothing. Bot-made rooms are capped (members, budget; `comms` in `config.json`), marked with who made them, and only you can delete them. Residual: you are the control, so a card you allow without reading is allowed; the card names the bot, the members and the budget, flags a run that read outside content, and shows bot-written text (the room name) flattened, stripped of markup and clipped, labelled as the bot's own. What you allow is exactly what is created: the plan is frozen at the card and re-checked when you answer.
- **A model chosen by a lead never buys autonomy or an upgrade.** `model` on `ask`, `tell`, `bot_send` and `room_post` is limited to sonnet, opus, haiku or auto, applies to that one task, leaves the approval ceiling untouched (the delegated task is never looser than its caller), and may not be dearer than the target agent's own model setting (an `auto` or sonnet agent cannot be pushed to opus; the engine also clamps router picks and `/opus` prefixes in bot messages to that ceiling). The room budget guard (checked before each turn, minimum budget $0.05) bounds the cost in rooms.
- **BSV wallet status, policy and the native confirmation.** BSV mode has no spend tool: Legion's own code has no way to sign, send, read balances or hold funds in this version (an agent's ordinary tools, a shell or a web fetch, are outside that statement and rest on their approval cards). What exists: a read-only status check of a wallet on a loopback address (four harmless questions; no default address, and nothing is contacted until the owner types the address and presses Connect, confirmed in a native dialog; the answer is the wallet's own claim, is treated as untrusted text, and its version is shown only if it is valid semver), a policy engine with tiny caps that nothing uses yet (it copies every request and answer on the way in), a tamper-evident audit log with a head anchor beside it, and a policy file whose SHA-256 is recorded in that log, so a policy file changed outside Legion loads as default limits and frozen (or freezes the chain while running). Every change to BSV policy state that could loosen anything (arm, disarm, unfreeze, limits, allowlist, Connect) needs a second per-launch secret, the NATIVE secret (line 2 of the core's stdin, held only by the Electron main process, never given to the window, env, argv, a file or a log), in addition to the admin secret; main shows a native confirmation dialog it words itself before arming, unfreezing or loosening anything, and Freeze, Disarm and Disconnect act at once (Freeze also works on a core with no app, with the bearer token, because it can only stop things). Residuals: a same-user process can read both secrets from memory, click the native dialog, rewrite the audit log together with its hashes (the log is tamper-evident, not tamper-proof) or call your wallet directly; the wallet's own prompts remain the real last gate for any spend; whether BSV Desktop answers the four status methods without a prompt, and what its prompts say, is unverified: Legion has not been pointed at the real wallet; the Electron dialogs were tested through a stub, not on a desktop. See `docs/BSV-MODE.md` and `docs/BSV-WALLET-DESIGN.md`.
- **Credentials.** Legion never reads or stores your Claude account credentials. In the default mode it relies on the account Claude Code is signed in to. If you choose `api-key` mode, the key is stored in `config.json`; boat.dev API keys are too. Keep that file private.
- **Known limits (same-user attacks).** The two-secret split stops the easy attack: a bot with a Bash tool reads `config.json` and calls the API as you. It does not stop a process that runs as your operating-system user and is willing to attack Legion itself: it can read the memory of the Legion app or its core (a debugger or `ReadProcessMemory`, `ptrace` on Linux) and take the admin secret, synthesize input to the window and click Allow, edit the installed JavaScript and wait for the next launch, stop Legion and run its own core, read `~/.claude` credentials, or call your BSV wallet on `127.0.0.1:3321` directly, or send code to the Blender add-on's socket on `127.0.0.1:9876` directly (no password; see the Blender residuals below), neither of which has any Legion code in front of it. `config.json` also still holds `boat.apiKey` (and the Claude API key in `api-key` mode) in plaintext, and any agent's Read tool can read it without a card. Only OS isolation stops these: run Bash-capable agents in a boat.dev VM or under a separate operating-system account, and do not give a Bash tool to an agent that reads untrusted web content. Every BSV spend is still confirmed in your own wallet. A scoped per-run token, DPAPI or a named pipe were considered and add nothing against a same-user attacker. See `docs/LIBRARY.md`.
- **Known limits of the Library's safety rules** (the full list is in `docs/LIBRARY.md`): the same-user limits above; seed-phrase detection knows only the English BIP-39 list and is a guard against mistakes, not against a bot hiding a secret; taint follows file tools only (a tainted run's Bash-made or copied files are not tracked) and the tainted-path list is a file a same-user bot can edit; a plain new file a bot planted in a vault you then import becomes your note, and a file you imported earlier that a bot rewrites updates in place on the next import; the lock file protects processes on one machine only.
- **Blender Bridge residuals** (details in `docs/BLENDER.md`). **The Blender add-on's socket has no password**, the same class of limit as the BSV wallet on `127.0.0.1:3321`: while the add-on's server runs in Blender, any program on your computer can send Python to `127.0.0.1:9876` (or the port you set) without Legion's card, static check, backup or audit line, and Legion's own code cannot add authentication to a downloaded add-on. Legion prefers the official stdio backend, connects to the community socket only while a call runs, and checks that the peer answers like the add-on, but none of that stops another local program; stop the server when you are not using the bridge. The static check on Blender scripts is a filter, not a sandbox: an approved script in live Blender runs with your user's rights and can wreck the open scene, loop or use all memory, and the check cannot know every Blender API that evaluates a string. The card showing the full script, the `.blend` backup and the default VM sandbox are the real controls. The raw Blender MCP servers are forbidden to agents by name (and for config-defined servers that mention Blender); a connector under an unrelated name is not covered. Exported `.blend` files can carry runnable code, so sandbox `.blend` exports are quarantined (`blender-quarantine/`, `.untrusted`) and live scripts cannot open, append or link one. The audit log is append-only by Legion's code and hash-chained, but the chain is unkeyed: the `.head` anchor file catches a cut-off tail, not a same-user process that rewrites both files. Downloads are https and public-host only with a size cap, but the resolved IP is not re-checked (DNS rebinding); the official server is pinned to a tag and sha256 and its Python dependencies are locked (`uv --frozen`) after Set up, the community add-on's address is a moving branch and is trusted on first use, and a changed download is refused until you press Trust the new download. A link swapped between a check and a write can still win a race. The official Blender Lab MCP server is GPL-3.0-or-later and is downloaded only on request, never bundled.
- **Agents run code.** Approval modes (`ask`, `auto-edits`, `full`) control what an agent may do on your machine without asking. `full` disables prompts for that agent. Use VMs for untrusted work.
- **Renderer.** The Electron window is sandboxed with context isolation and no Node integration.

Reports about these boundaries (for example an authentication bypass, a way to reach the API from a web page, or a secret leaking into logs or API responses) are in scope.
