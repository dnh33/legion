# BSV mode: what it is today

BSV mode is an optional toggle, off by default, in testnet knowledge mode. This page is the plain truth about it; the pack lesson `bsv-status-today` says the same to the Assayer. The design of the next, reviewed phase (human-approved reads, a manual testnet spend) is in `docs/BSV-WALLET-DESIGN.md`; none of it ships until the owner has answered the questions at its end.

## What it holds

- The toggle (`src/core/bsv/`). Turning it on shows the Assayer bot, loads or upgrades the bundled knowledge pack in the Lattice scope `bsv` (also at core start when it is already on), and gives the Assayer a four-line preamble. Turning it off hides the Assayer and the scope again (the nodes are kept) and cancels the Assayer's queued runs.
- The Assayer: an advisory bot whose one BSV tool is `bsv_status` (below). It explains, drafts and reviews. It is still an ordinary Legion agent: approval `ask` by default, VM off by default, and the normal Claude tools. In `ask` mode shell commands and file edits need your approval, while web fetch, web search and read-only tools (read, glob, grep) run without a prompt; you can switch its approval to `full`, which removes the prompts (see `src/core/approvals.ts`). Legion's own code has no tool that signs or sends BSV, and a human does every wallet step, in their own wallet. That is a statement about Legion's code, not about the Assayer's good behaviour: its ordinary tools (a shell, a web fetch) are outside it and are limited only by their approval cards (or by nothing, in `full`).
- `bsv_status` (`src/core/bsv/wallet-tool.ts`, MCP server `legion_bsv`, Assayer only, only while BSV mode is on). A read-only check of whether a wallet answers on this computer. It takes no arguments and returns `{reachable, authenticated, network, version, height}` plus one calm sentence. The probe (`src/core/bsv/wallet-probe.ts`, the only file allowed to name wallet methods or the wallet port) sends exactly four harmless questions, each `POST /<method>` with the body `{}` and the origin `legion.local`: `getVersion`, `getNetwork`, `isAuthenticated`, `getHeight`. Legion's own probe has a method list that holds nothing that lists outputs, reveals a key, or creates, signs or sends a transaction, and every outgoing name is checked against it. **There is no default wallet address and no automatic probe.** The owner types the address in the BSV panel and presses **Connect**; the app shows a native confirmation that names the address, and only then does the core send the four questions. The connection lives in memory only, so every launch starts disconnected, and Disconnect, a freeze, or turning BSV mode off disconnects again. The address is kept as `bsv.walletUrl` in `config.json` (so the panel can prefill it) and is accepted only if it is a loopback `http` address with nothing else in it (no credentials, path, query or redirect following). The `version` it reports is shown only when it is a semantic version (`1.2.3`, with an optional `-prerelease` and `+build`); anything else is dropped. A "changed" report from the wallet (another network than last time) is an unverified claim and can only make Legion more careful: it disarms. It never raises a limit, lifts a freeze or resets anything. Limits: 1.5 s per call, 4 s in all, 4 KiB of body, at most one real probe every 5 s (single flight, no retry loop), six `bsv_status` calls per task, and nothing at all while BSV mode is off. A wallet on mainnet while Legion is in testnet mode gives the warning "The wallet is on MAINNET; Legion is in testnet knowledge mode; Legion will not use it." and nothing else changes. The answer is the wallet's own claim and is treated as untrusted text: the run is tainted like any outside content, so what it writes to the library is stored as untrusted. The tool is not a Legion-trusted name, so in ask mode it needs your approval like any other non-Legion tool. The same answer is on `GET /api/bsv/wallet` for the app.
- The policy engine (`src/core/bsv/policy.ts`), pure and unit-tested, connected to NO tool. Per-transaction, per-session and rolling-24-hour caps (pending requests count), a recipient allowlist, a maximum number of outputs and a fee ceiling; defaults are tiny (1,000 / 5,000 / 10,000 sat, 3 outputs, 200 sat fee) and the hard ceilings (1,000,000 / 5,000,000 / 10,000,000 sat, 10 outputs, 10,000 sat fee) are constants in code that no setting, file or route can exceed. Mainnet arming is a short expiry (5, 15, 30 or 60 minutes) held in memory only, tracked on both a monotonic and the wall clock (the earlier end wins), so a restart disarms it. Freeze disarms, denies everything pending and blocks new requests. The engine never answers "allow": the best verdict is "needs approval". Requests carry idempotent ids, a card hash binds an approval to the decoded transaction, and a run that read untrusted content needs an extra confirmation. Every request and answer is copied on the way in (and the stored decision on the way out), so a caller that keeps a reference cannot lower a required confirmation or change an amount after it was checked. Today nothing calls it, because there is no spend tool; arming changes policy state and nothing else.
- The audit log (`src/core/bsv/audit.ts`), `bsv/audit.jsonl` in Legion's data folder: append-only, one JSON line per BSV decision (agent, task, tool, decision, reason, redacted fields; never a key, seed phrase or wallet answer body), each line carrying the SHA-256 of the line before it. It is tamper-evident, not tamper-proof (a program running as you can rewrite the whole file, its hashes and the anchor). Beside it, `audit.jsonl.head` records the last sequence number and hash after every write; at the next start a log that ends earlier than the anchor says, was emptied, or ends in a different line is reported in the log's own next line (`head-mismatch`) and freezes the chain. A log that fails verification at start is moved aside (kept as evidence), a new chain starts and the chain is frozen. A torn last line (a crash mid-write) is tolerated. The rolling 24-hour spend window is rebuilt at start from every file of the log (current, rotated, kept evidence) by the time written in each entry (rather than from the last N lines in file order), so after a flood of status notes, a rotation or a restored file every recorded spend is still inside the window. Read it with `GET /api/bsv/audit` or the Activity list in the BSV panel.
- The policy file (`bsv/policy.json`) is checked against the SHA-256 that Legion last recorded in the audit log when it wrote it. At start, a file that is unreadable, has no record, or differs from the record (or a record with no file) loads as default limits, an empty allowlist and **frozen**, and the file is kept aside as `policy.json.tampered-<time>` (at most 10 are kept). While running, the same check runs before every policy read or change and before every `bsv_status`: a changed or removed file freezes the chain at once, and Legion writes its own in-memory copy back. A same-user program that can rewrite both the file and the audit log is a documented residual.
- Owner controls. Arm, disarm, unfreeze, limits, the allowlist and Connect change only through the Electron app (**Freeze** and **Disconnect** also work without it, see below): the window asks the main process (`legion:bsv-policy`), which parses the request strictly, reads the current policy from the core itself, shows a NATIVE dialog it words itself (Cancel is the default button), and only then calls the core with a second per-launch secret that the window never holds. Freeze, Disarm and Disconnect only make things safer, so they act at once without a dialog. Freeze also works on a core that no app started (headless): it needs only the bearer token, because it can only stop things. See "What the token split does and does not cover".
- The pack (`src/core/kg/seeds/bsv.json`, 157 nodes in 8 modules). Bots can read it. They cannot change its notes or its links, and cannot link onto it (`kg_link` to a `bsv` note is refused); only you can. The Assayer reads it with `kg_recall` and `scope: "bsv"`.
- `bsv-status-today`, `bsv-wallet-choice` and the safety lessons. Lessons about a later wallet phase are marked **`props.built:false`**, have a title that starts with **`[Design]`** (so a title in a related line or a briefing cannot read as fact), carry the `design` tag, start with "Design, not built in v0." and sit at confidence 0.6. Lessons about controls that exist in part are marked **`props.built:'partly'`**, start with **`[Partly built]`**, open with "Partly built: some of this exists, the rest is design." and have a "Built today" and a "Not built" part. The Assayer is told never to say a control exists beyond what `bsv-status-today` lists.

## What it does NOT do

No keys or seed phrases, no signing, no broadcasting, no balance or output reads, no spend tool and no approval card for spends. The only network call BSV mode can make is the four-question status probe to a loopback address (and the app's own calls to its local core). Legion's mode is always testnet (`BsvNetwork` is the literal `testnet`); "armed" is a policy state that nothing consumes yet.

While BSV is off the Assayer is hidden everywhere and cannot be run: `/api/state` and the task routes (a task of the Assayer answers 404 like an id that never existed), the event stream (SSE), MCP (`legion_run`, `legion_continue`, `legion_vm`, `legion_status`, `legion_cancel`, `legion_recent_tasks`), the comms hub (`bot_list` omits it, `bot_send` to it says "Unknown bot" and creates nothing, a room it belongs to is dormant until it is back, and it cannot be added to a room), and the HTTP routes that start a task or drive its VM. A run of the Assayer that is waiting in the queue when you turn BSV off is cancelled (and the engine checks again when a queued job is about to start). Not hidden: the agent record by id (you can still edit or delete it in Settings), `GET /api/bsv` (it reports `assayerAvailable` for the toggle's own UI), and a run that was already in progress when you switched off, which finishes (its `bsv` notes are no longer readable to it).

### What the tripwire checks, and what it cannot

`test/bsv-tripwire.test.ts` and `test/bsv-review-tripwire.test.ts` (scanner: `test/bsv-scan.ts`) fail the build when ANY file under `src/` or `ui/src` (core, comms, kg, the UI, the electron shell and the stdio proxy) other than the one wallet probe contains `3321`, `WalletClient`, `HTTPWalletJSON`, `@bsv/sdk`, `createAction` or any wallet method name (`signAction`, `listOutputs`, `getPublicKey`, `internalizeAction`, `createSignature` and the rest of the BRC-100 list). The probe file may name only its four allowlisted harmless methods and the wallet port, and is classed as a loopback-only HTTP client (it may not open a server, spawn a process or touch a non-loopback host). Everywhere else the scan also fails on imports `@bsv/*`, uses `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` or an MCP client transport, imports a socket module (`https`, `http2`, `net`, `tls`, `dgram`, `dns`, `undici`, `axios`, `ws` and the like) or `child_process`, uses string decoding that can hide a name (`String.fromCharCode`, `atob`, base64), or registers a tool whose name is not a string literal or is wallet-shaped (a word such as `wallet`, `bsv`, `spend`, `pay`, `sign`, `broadcast`, `arm`, `freeze`). The only files allowed to do any of the network or process things are listed, each with its reason, in `ALLOWLIST` in `test/bsv-scan.ts`: the boat.dev client, the local HTTP/SSE/MCP server, the electron shell and the stdio proxy (both only talk to the core on 127.0.0.1), the UI's client of the local core, and the secret detector (decoding). A new file that needs one of these fails until someone adds it there, on purpose.

It spots names spelled in pieces (`'Wallet' + 'Client'`, `['Wallet','Client'].join('')`, `concat`, template parts, reversed strings, `replace` and `slice` of a literal, `\u0073` and `\x73` escapes), aliases of the network globals and computed access to them (`globalThis['fetch']`), and dynamic imports. Inside the BSV code (`src/core/bsv`, `ui/src/bsv`, `src/shared/bsv-*`, the Electron admin logic) it is stricter: a quoted identifier-shaped token that names signing, spending, broadcasting or inscribing is refused, as is a computed member built from pieces or a template, a computed call (`x[k]()`), `eval`, `Function`, `Reflect`, `this[...]` or `globalThis[...]`, and non-ASCII look-alike letters in code. No wallet port exists in any source: the probe has no default address, so `3321` is refused everywhere. It is a static scan, not a sandbox. It cannot stop a name assembled from data at run time, an `eval`, code in a dependency, or a shell command an agent runs through a tool it already has (the Assayer's Bash, or `legion_vm exec` in a VM): those are bounded by approvals, not by this test.

## Pack versioning

The pack has a `version` (now 7). The version is stored on the index node (`props.seedVersion`) and every seeded node carries `props.seedHash`, a hash of what the pack said: title, body, tags, confidence, type, scope, props (without the seed's own bookkeeping) and sources. The upgrade runs when you toggle BSV on, when you press **Load BSV pack**, and once at core start when BSV is already on (idempotent, logged, never blocks boot and never throws).

- Nothing loaded: every node is added.
- An older version loaded: missing nodes are added; nodes you never edited take the new text; nodes you edited (any of the fields above) are left alone and returned as `skippedEdited`; links that are missing are added, links that exist are never touched (your note or weight on a pack link stays). The toast and the API result say what happened (`loaded`, `upgraded`, `repaired`, `already-loaded`, and the counts).
- The same version loaded: nothing is rewritten, so a plain re-seed never touches your edits. A node that is simply missing is put back (`repaired`).
- Crash safety: nodes are written first, then links, and the index node (the version marker) last. A process that dies half way leaves an install that the next toggle, button press or start still upgrades.
- What you deleted stays deleted. Deleting a pack node, or a link between two pack nodes, or changing the relation of a pack link, is remembered (`seed-removed.json` beside the graph log); an upgrade does not bring it back and lists it as `skippedRemoved`. A node a human merged into another stays as the retired note it became: the upgrade neither rewrites nor revives it and lists it under `skippedEdited`.
- To take the pack text for a node, or to bring one back, ask for it by id: `POST /api/kg/seed/bsv {"restore":["bsv-tx-fees"]}` (BSV mode on). A deleted node comes back with its links; a node you edited is reset to the pack text. Unknown ids are refused (400) and nothing is written. Plain "delete the node and toggle again" does NOT bring it back: that is what the ledger is for.
- A node the new pack dropped is never deleted or archived: that is your call. A snapshot of the graph log is taken before anything is written.
- "Edited" means the current node no longer matches the stored `seedHash`. A node seeded with the first, narrower hash (title, body, tags, confidence) is compared on those fields only. An install from before hashes counts a node as untouched when it was never changed or still matches a text an earlier pack shipped (`seeds/bsv-legacy-hashes.json`). An archived or superseded pack node counts as edited.

## What the token split does and does not cover

Turning BSV mode on or off (`POST /api/bsv`) and every Library route need the admin secret that only the Legion app window holds, so reading `config.json` is no longer enough to flip the switch or accept its own notes. Every BSV policy change (arm, disarm, freeze, unfreeze, limits, allowlist) needs a second secret as well, the NATIVE secret: a second line on the core's stdin, held only by the Electron main process and never given to the window, an environment variable, argv, a log or a file. The core checks it in constant time and refuses with 403 without it, so neither the bearer token nor the admin secret that the window holds can arm, unfreeze, change limits or connect a wallet (the one thing the bearer token can do is Freeze, which only stops things), and a compromised page in the window cannot arm or unfreeze on its own: the request has to pass main's strict parser, its sender check (only the window's own page, not a navigated or foreign frame) and its native confirmation dialog. What this does NOT stop: a process running as your own user can still read Legion's memory (both secrets), edit its files, synthesize clicks on the native dialog, or call your BSV wallet directly on `127.0.0.1:3321`, which Legion cannot see. Only a VM or a separate OS account stops that, and the wallet's own prompts remain the real last gate for any spend. If the core was not started by the app (no native secret), policy changes are locked and the panel says so.

## Not built (design only)

Any spend tool (it would be a new tool name, a new allowlist entry and a new owner review), the connection of the policy engine to a wallet call, human-approved wallet reads (balances, outputs), the approval card for a spend, the testnet two-stage spend flow, a form for changing limits and the allowlist in the panel (the Electron bridge supports it; the form is not built), the VM boundary for wallet tools. The design, the threat model, what each safeguard blocks, the residual risks, the adversarial test plan and the exact questions for the owner are in `docs/BSV-WALLET-DESIGN.md`. The wallet choice plan is in the pack lesson `bsv-wallet-choice` (BSV Desktop first, HandCash BRC wallet beta second, BSV Browser later; never Yours/Panda, the old Metanet Desktop, bsv-mcp or any wallet that holds keys for Legion; never grant a monthly limit or auto-pay; two-stage approval, Legion's card then the wallet's own prompt; originator `legion.local`; `@bsv/sdk` `WalletClient` only, not wallet-toolbox) and in the research note `bsv-wallets.md` kept with the project docs. None of it ships until you have reviewed the wallet phase.

## Not verified

Legion has never talked to the real BSV Desktop wallet, and has never been pointed at it. The owner's machine holds a funded one, so tests use a fake loopback wallet on a random port, nothing that runs automatically may touch port 3321, and Legion itself contacts no wallet until the owner presses Connect. Unverified: whether BSV Desktop answers the four status methods without a permission prompt, what its prompts say, which origin rules apply (the origin is self-declared), and the exact response shapes of a real wallet. The probe treats an unexpected answer as "network unknown" and never as testnet. The Electron dialogs are tested through a stub (`test/electron-emu`) that records the options main passes; they were not shown on a real desktop.

## The interface

Static by design (a performance requirement, enforced by `test/bsv-ui-view.test.ts`): nothing in the BSV UI animates, and the only timers are the status poll (every 60 s, only while the window is visible and focused, and a re-render only when an answer changed) and the countdown (once a second, only while mainnet is armed and the window is visible and focused). Testnet: a calm cyan line along the title bar and a small text readout (`TESTNET`, and `block N` when a testnet wallet reported a height). Armed: a static amber frame around the window, an amber title-bar line, and a pill with the countdown, a **Freeze chain** button (also shown whenever a request is pending), **Disarm** and **Details**. A wallet on mainnet shows the warning pill without the amber frame. The BSV panel (the PANEL button next to the switch, the pill's Details, or the command palette) shows the wallet status with an address box, a Connect button (a native confirmation first) and, once connected, Disconnect and Check now, arming with a choice of duration, Freeze and Unfreeze, the limits, and the Activity list with the log's verification status and a Save log as file button. There is also a tray item, Freeze BSV chain.

## BSV pack refresh

A human release step, never a runtime fetch: nothing in Legion downloads pack text. To refresh, re-read the primary sources, edit `seeds/bsv.json`, bump `version` (an unchanged version never rewrites existing nodes), and ship. Sources to re-check: the BSV Association docs hub (docs.bsvblockchain.org) and the BRC index (bsv.brc.dev), ts-stack (README, package manifests on npm: `@bsv/sdk`, `@bsv/wallet-toolbox`, `@bsv/simple`), the BSV Desktop repo and README (licence, ports, permissions), the HandCash BRC wallet docs, the Teranode repository and release notes (version, licence, networks), the Chronicle release page and node release notes (activation facts that are press-sourced), the ARC repository (bitcoin-sv/arc), and the 1Sat docs and SDK. Keep `props.verify` labels honest, keep controls that do not exist marked `built:false` and controls that exist in part marked `built:'partly'`, and run `npm test` (the seed tests refuse unmarked design claims, a design node without its `[Design]` title, unhedged claims of a control Legion does not have, and leftover Update/Correction paragraphs).
