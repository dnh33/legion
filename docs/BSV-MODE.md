# BSV mode: what it is today

BSV mode is an optional toggle, off by default. The knowledge it teaches defaults to testnet. Legion's own code also contains a spend tool for testnet and for mainnet; mainnet is built behind a hard-off switch that ships OFF. This page is the plain truth about it; the pack lesson `bsv-status-today` says the same to the Assayer. The design and its history are in `docs/BSV-WALLET-DESIGN.md` and `claude/plan-bsv-rung3.md`.

**Testing preview.** BSV mode has been tested with fake wallets only, not yet with a real wallet or real funds. Use a testnet wallet with test coins. Feedback and ideas are very welcome: open an issue at github.com/dnh33/legion (see [CONTRIBUTING.md](../CONTRIBUTING.md)).

**Not verified.** The spend tool was built and tested against fake wallets only. It has not been verified against a real wallet or with real funds until the owner's checks are recorded in `claude/tracker-pc-checks.md` (V1 to V12 on a separate testnet wallet, R0 to R11 by hand with a tiny amount, ND1 to ND11 for the dialogs). Legion's code, tests and agents have never been pointed at the owner's real, funded wallet.

## What it holds

- The toggle (`src/core/bsv/`). Turning it on shows the Assayer bot, loads or upgrades the bundled knowledge pack in the Lattice scope `bsv` (also at core start when it is already on), and gives the Assayer a four-line preamble. Turning it off hides the Assayer and the scope again (the nodes are kept) and cancels the Assayer's queued runs.
- The Assayer: a bot with two BSV tools, `bsv_status` (read-only, below) and `bsv_spend_request` (the Spend section). It explains, drafts and reviews. It is still an ordinary Legion agent: approval `ask` by default, VM off by default, and the normal Claude tools. In `ask` mode shell commands and file edits need your approval, while web fetch, web search and read-only tools (read, glob, grep) run without a prompt; you can switch its approval to `full`, which removes the prompts (see `src/core/approvals.ts`). Legion's own code holds no key, signs nothing itself and broadcasts nothing itself: one tool asks a wallet to build and sign ONE transaction, only after your own confirmations; whether the wallet asks too depends on the wallet (Residual risks). That is a statement about Legion's code, not about the Assayer's good behaviour: its ordinary tools (a shell, a web fetch) are outside it and are limited only by their approval cards (or by nothing, in `full`). A wallet reachable from a shell or a web tool is not covered by any of this.
- `bsv_status` (`src/core/bsv/wallet-tool.ts`, MCP server `legion_bsv`, Assayer only, only while BSV mode is on). A read-only check of whether a wallet answers on this computer. It takes no arguments and returns `{reachable, authenticated, network, version, height}` plus one calm sentence. The probe (`src/core/bsv/wallet-probe.ts`, the only file allowed to name wallet methods or the wallet port) sends exactly four harmless questions, each `POST /<method>` with the body `{}` and the origin `legion.local`: `getVersion`, `getNetwork`, `isAuthenticated`, `getHeight`. Legion's own probe has a method list that holds nothing that lists outputs, reveals a key, or creates, signs or sends a transaction, and every outgoing name is checked against it. **There is no default wallet address and no automatic probe.** The owner types the address in the BSV panel and presses **Connect**; the app shows a native confirmation that names the address, and only then does the core send the four questions. The connection lives in memory only, so every launch starts disconnected, and Disconnect, a freeze, or turning BSV mode off disconnects again. The address is held in memory only (a `bsv.walletUrl` written into `config.json` by hand is ignored, so a hand-edited file cannot choose where Legion connects) and is accepted only if it is a loopback `http` address with nothing else in it (no credentials, path, query or redirect following). The `version` it reports is shown only when it is a semantic version (`1.2.3`, with an optional `-prerelease` and `+build`) or a short lower-case vendor token followed by one (the real BSV Desktop answers `wallet-brc100-1.0.0`: at most 32 token characters, at most 64 in all); anything else is dropped. A "changed" report from the wallet (another network than last time) is an unverified claim and can only make Legion more careful: it disarms. It never raises a limit, lifts a freeze or resets anything. Limits: 1.5 s per call, 4 s in all, 4 KiB of body, at most one real probe every 5 s (single flight, no retry loop), six `bsv_status` calls per task, and nothing at all while BSV mode is off. A wallet that says it is on mainnet gives the warning "The wallet says it is on MAINNET (real funds). In Legion's own code a mainnet spend needs the mainnet switch (off by default), Arm and your confirmations; whether the wallet asks too depends on the wallet." and nothing else changes. The answer is the wallet's own claim and is treated as untrusted text: the run is tainted like any outside content, so what it writes to the library is stored as untrusted. The tool is not a Legion-trusted name, so in ask mode it needs your approval like any other non-Legion tool. The same answer is on `GET /api/bsv/wallet` for the app.
- The policy engine (`src/core/bsv/policy.ts`), pure and unit-tested, used by the spend tool (it holds no I/O of its own). Per-transaction, per-session and rolling-24-hour caps (pending requests count), a recipient allowlist, a maximum number of outputs and a fee ceiling, kept per network (the numbers are in the Spend section and in `src/core/bsv/networks.ts`); the hard ceilings are constants in code that no setting, file or route can exceed. Mainnet arming is a short expiry (5, 15, 30 or 60 minutes) held in memory only, tracked on both a monotonic and the wall clock (the earlier end wins), so a restart disarms it; one arm covers one mainnet spend. Freeze disarms, denies everything pending and blocks new requests. The engine never answers "allow": the best verdict is "needs approval". Requests carry idempotent ids, a card hash binds an approval to the decoded transaction, and a run that read untrusted content needs an extra confirmation. Every request and answer is copied on the way in (and the stored decision on the way out), so a caller that keeps a reference cannot lower a required confirmation or change an amount after it was checked. Legion's own code runs every spend request through it, on the values it decodes from the wallet's unsigned transaction, not on the agent's numbers.
- The audit log (`src/core/bsv/audit.ts`), `bsv/audit.jsonl` in Legion's data folder: append-only, one JSON line per BSV decision (agent, task, tool, decision, reason, redacted fields; never a key, seed phrase or wallet answer body), each line carrying the SHA-256 of the line before it. It is tamper-evident, not tamper-proof (a program running as you can rewrite the whole file, its hashes and the anchor). Beside it, `audit.jsonl.head` records the last sequence number and hash after every write; at the next start a log that ends earlier than the anchor says, was emptied, or ends in a different line is reported in the log's own next line (`head-mismatch`) and freezes the chain. A log that fails verification at start is moved aside (kept as evidence), a new chain starts and the chain is frozen. A torn last line (a crash mid-write) is tolerated. The rolling 24-hour spend window is rebuilt at start from every file of the log (current, rotated, kept evidence) by the time written in each entry (rather than from the last N lines in file order), so after a flood of status notes, a rotation or a restored file every recorded spend is still inside the window. Read it with `GET /api/bsv/audit` or the Activity list in the BSV panel.
- The policy file (`bsv/policy.json`) is checked against the SHA-256 that Legion last recorded in the audit log when it wrote it. At start, a file that is unreadable, has no record, or differs from the record (or a record with no file) loads as default limits, an empty allowlist and **frozen**, and the file is kept aside as `policy.json.tampered-<time>` (at most 10 are kept). While running, the same check runs before every policy read or change and before every `bsv_status`: a changed or removed file freezes the chain at once, and Legion writes its own in-memory copy back. A same-user program that can rewrite both the file and the audit log is a documented residual.
- Owner controls. The mainnet switch, arm, disarm, unfreeze, limits, the allowlists and Connect change only through the Electron app (**Freeze** and **Disconnect** also work without it, see below): the window asks the main process (`legion:bsv-policy`), which parses the request strictly, reads the current policy from the core itself, shows a NATIVE dialog it words itself (Cancel is the default button), and only then calls the core with a second per-launch secret that the window never holds. Freeze, Disarm, Disconnect and switching mainnet OFF only make things safer, so they act at once without a dialog (switching it ON shows a warning dialog). Freeze also works on a core that no app started (headless): it needs only the bearer token, because it can only stop things. See "What the token split does and does not cover".
- The pack (`src/core/kg/seeds/bsv.json`, 167 nodes and 745 links, version 10). Bots can read it. They cannot change its notes or its links, and cannot link onto it (`kg_link` to a `bsv` note is refused); only you can. The Assayer reads it with `kg_recall` and `scope: "bsv"`.
- `bsv-status-today`, `bsv-wallet-choice` and the safety lessons. Lessons about a later wallet phase are marked **`props.built:false`**, have a title that starts with **`[Design]`** (so a title in a related line or a briefing cannot read as fact), carry the `design` tag, start with "Design, not built in v0." and sit at confidence 0.6. Lessons about controls that exist in part (the spend flow, per-network limits, the dialogs, the unknown-outcome rule, the owner's checks and others) are marked **`props.built:'partly'`**, start with **`[Partly built]`**, open with "Partly built: some of this exists, the rest is design." and have a "Built today" and a "Not built" part. The Assayer is told never to say a control exists beyond what `bsv-status-today` lists.

## Spend

One tool, `bsv_spend_request` (`src/core/bsv/spend.ts`, MCP server `legion_bsv`, Assayer only, only while BSV mode is on). It asks your wallet to build, and after your confirmations to sign, ONE payment to ONE address. It works on testnet and on mainnet. **Mainnet is built and switched OFF**: in a fresh install the switch is off, only you turn it on (Legion app, native warning dialog, Cancel is the default), turning it off needs no dialog, and each mainnet spend needs its own Arm. The spend tool was built and tested against fake wallets only. **It has not been verified against a real wallet or with real funds until your checks are recorded** (V1 to V12, R0 to R11, ND1 to ND11 in `claude/tracker-pc-checks.md`). Treat Legion's last dialog as the per-spend gate on both networks: whether the wallet asks too depends on the wallet, and Legion's own code cannot see it.

> **What a real wallet was seen to do** (by hand on 2026-10-02, read-only, on the owner's own BSV Desktop; no Legion code, test or agent was involved). `getVersion` answered `wallet-brc100-1.0.0` (not semantic versioning, so the probe accepts a short vendor token followed by a version). `getNetwork` answered `mainnet`. The four read-only methods (`getVersion`, `getNetwork`, `isAuthenticated`, `getHeight`) answered HTTP 200 with a JSON body labelled `text/html` (Legion does not look at the content type) and showed **no prompt**. **What the BRC-100 text says** (read 2026-10-02 at hub.bsvblockchain.org/brc/wallet/0100): `createAction` with signing switched off returns a signable transaction, `tx` as Atomic BEEF and a `reference`, and has no fee, input or change fields, so Legion decodes the BEEF itself; `signAction` takes the `reference`; `abortAction` takes the `reference` and returns `{aborted: true}`; errors carry `status`, `code` and `description`. **What it leaves open** (so these are checks, not facts): whether the wallet prompts for signing every time, what a decline looks like, and the shape of its change output. A `reference` that is lost in a crash cannot be resumed or aborted through the public interface. BSV Desktop serves BRC-100 over HTTPS on 2121 and also answered plain HTTP on 3321 on a test PC; it keeps testnet in a separate database from mainnet.

### The tool

- **Input** (checked by `zod`, and the raw keys are checked again): `requestKey` (8 to 64 characters, `A-Za-z0-9_-`, makes a request idempotent), `recipient` (one base58 address), `sats` (an integer, the limits decide how much), `purpose` (up to 200 characters, shown to you as the agent's own words, never used for any decision). **Any other key, a `network` field included, is refused (`extra-input`).** The network is never an input.
- **Result**: `<bsv-spend-result untrusted="true">{...}</bsv-spend-result>` plus one fixed sentence. The JSON has the request id, the network label, a status word (`denied`, `pending-owner`, `pending-wallet`, `declined`, `expired`, `failed`, `unknown`, `executed`), fixed reason codes (the list is `SPEND_REASON_CODES` in `spend.ts`) and a transaction id only if it is 64 hex characters. No wallet text, script, reference, card hash or engine message ever reaches the agent; the run is marked tainted after any wallet contact. The same `requestKey` returns the stored status and makes no new wallet call; a different payload under a used key is refused. The tool waits at most 100 seconds, then answers `pending-owner` or `pending-wallet`; the request itself is owned by the service, so a cancelled run or a short tool timeout cannot orphan it.
- **Who may ask**: a run you started in the app. A run started by another bot, a room, the bridge or an MCP client is refused (`not-human-run`).

### The flow

1. **Gates** (no wallet contact, nothing reserved if one fails): BSV mode on; the Assayer; a run you started; not frozen; no unknown outcome pending; one request in flight; at most 3 requests per task and 5 per 10 minutes; only the four input keys; a base58check address.
2. **Written first**: a `proposed` line in the audit log. If it cannot be written, nothing goes to the wallet.
3. **Fresh probe**: the wallet must be connected, reachable and signed in, and its network claim (`test`, `main`, or unknown) is pinned into the request. Unknown: refused. `main` with the switch off: refused (`mainnet-disabled`) with zero build calls; switch on but not armed: refused (`not-armed`). The recipient's address version byte must belong to the pinned network (`address-network-mismatch`).
4. **Unsigned build**: the wallet is asked to build the transaction without signing (`createAction`, 256 KiB cap; a wallet may hold this call while it asks you for a spending grant, and BRC-219 says an app should not time that out, so Legion waits up to a 15-minute safety cap; the BSV panel lists the request as waiting for your wallet, with Cancel; Deny, Freeze and Disconnect also end the wait, and a build the wallet finishes afterwards is released with `abortAction` (Legion's own code never shows or signs it); no answer within 15 minutes is `wallet-no-answer`, any other failure `build-failed`). Legion decodes it itself (bounded BEEF parser; inputs are priced from the parent transactions inside the BEEF; more than 100 inputs or outputs, a missing parent, a zero-sat output or anything unreadable is `undecodable`). It must hold exactly one output equal to the requested script and amount, plus at most ONE other standard P2PKH output, shown as change. That change output is **wallet-claimed; Legion cannot verify it.**
5. **Policy**: the engine checks and reserves on the DECODED numbers (allowlist, caps with reservations, fee ceiling, output count, network). Any denial aborts the wallet's build (`abortAction`).
6. **Card**: a card with a hash is held in the core for 120 seconds. The Legion app reads it from the core itself.
7. **Your dialogs** (below). Cancel, Escape or closing a box denies. A late Approve after expiry is refused.
8. **Re-checks at decision**: not frozen, hash equal, every confirmation given, a fresh probe still on the card's network (both directions), the run's taint re-read (a card made while clean is voided if the run became tainted), no unknown outcome, and for mainnet the switch still on and the arm still held. Approving a mainnet spend uses up the arm.
9. **`executing` is written** (strict), then a fresh probe again, then `signAction`. Whether the wallet asks here depends on the wallet (a wallet built on wallet-toolbox asks at step 4 instead, see Residual risks). Legion's own code does not answer a wallet prompt, does not retry the call and does not store the signed bytes, only the txid. The wait for the answer is 300 seconds.
10. **Verify**: the returned transaction is decoded again and compared with the card. A different amount or recipient: the chain freezes, mainnet is switched off and the status says so. Then `executed` is written (strict) and the reservation settles.

### The dialogs

Built by the Electron main process from a card it read from the core itself (never from the window), `Cancel` is the default and the Escape button on every one, `noLink` is set, and nothing the agent wrote is shown except the purpose line, labelled "Written by the agent. Not checked by Legion."
- **D1, the card**: the amount, the FULL recipient address (wrapped, never shortened), the network word (on mainnet, `MAINNET (LIVE FUNDS)`, the wallet's own claim), whether the address is on your allowlist, the fee, the change output with the wallet-claimed note, the total leaving the wallet, the limits left, the time left on the arm (mainnet) and a warning if the run read untrusted content.
- **D2, LIVE FUNDS** (mainnet only, always): a second box with another title, the confirm button FIRST and labelled with the amount and the last 8 characters of the recipient, repeating the network and the full recipient, and telling you to treat it as the last check (whether the wallet asks too depends on the wallet) and to keep any spending grant the wallet asks for one-time or at or below Legion's caps.
- **D3, untrusted content** (a separate press, only when the run read outside content; `bsv_status` taints a run, so in practice this appears almost every time).
- **Resolve** (unknown outcome, below): Cancel, "It was NOT sent", "It WAS sent"; the amount comes from the item main read.

A clean testnet spend is one dialog, plus whatever your wallet asks; a tainted one is two; a clean mainnet spend is two, a tainted one three. Before any of them, mainnet needs the switch and an Arm.

### Limits, per network

Every network has its own caps, allowlist, reservations and ledger, so testnet traffic never uses mainnet headroom (and the reverse). Defaults, and the hard ceilings that only a code change raises (`src/core/bsv/networks.ts`):

| | Testnet | Mainnet |
|---|---|---|
| Per transaction / per session / per 24 hours (default) | 1,000 / 5,000 / 10,000 sat | 1,000 / 2,000 / 5,000 sat |
| Payment outputs, fee ceiling (default) | up to 3 allowed by the engine (the tool sends 1), 200 sat | 1, 100 sat |
| Hard ceilings | 1,000,000 / 5,000,000 / 10,000,000 sat, fee 10,000 | 100,000 / 250,000 / 500,000 sat, fee 1,000 |
| Allowlist | up to 50, empty by default | up to 10, empty by default |
| Arm | not needed | needed, one spend per arm (5, 15, 30 or 60 minutes) |
| Dialogs | D1 (+ D3) | D1, D2 (+ D3) |

An empty allowlist denies every request. An allowlist entry whose version byte belongs to the other network is refused. Only you change limits and lists, in the app, after a native dialog.

### Mainnet is OFF unless you turn it on

`mainnetEnabled` lives in `bsv/policy.json`, inside the fingerprinted file (a missing, unreadable or tampered file loads it OFF and frozen). Only `POST /api/bsv/policy/mainnet` can turn it on, and it needs the admin secret AND the native secret (never the MCP token); turning it off needs the admin secret only. It turns itself OFF, disarms and freezes after: a mainnet request with an unknown outcome, a mismatch after signing, an audit failure on a mainnet request, a wallet that claims a different network just before signing, or a tampered policy file. A plain Freeze leaves the switch alone. The audit log is a second source: at start, if the last `mainnet-changed` line in the log says OFF and the file still says ON (a save that failed), it loads OFF (`test/bsv-fix-round.test.ts`, "B5 proof"). A hand edit of the file itself is a tamper: OFF and frozen.

### The unknown-outcome rule

A wallet may have signed before it stopped answering. A timeout, a reset connection, an unreadable answer, a freeze during the call or a restart while a signing call was open makes the request `unknown`. Legion's own code does not retry and does not re-send. **While any request is unknown, every spend on BOTH networks is blocked, and the block survives a restart** (the audit log's `executing` line with no `executed`, `failed` or `resolved` after it seeds it again at start, and freezes). If it was a mainnet request, mainnet is also switched OFF and disarmed. You clear it by reading your wallet's own history and choosing in a native dialog: "It was NOT sent" frees the reserved amount; "It WAS sent" keeps it counted. Only a `resolved` line inside an audit chain that verifies clears it at restart; a forged line in a broken file does not. A late answer (after a freeze, an expiry or an unknown outcome) is written as evidence (`late-answer`) and never changes the status.

### Audit lines

Every request writes `proposed` (strict: no line, no wallet call), `executing` (strict, before the signing call), `executed` (strict; if it fails to be written after a txid exists the chain freezes), and a line for each end (`denied`, `declined`, `expired`, `failed`, `unknown`, `late-answer`, `resolved`, `restored-unknown`, `network-flip-during-sign`). Every spend line carries the network and the request id, and holds no key, no signed bytes and no wallet text.

### What the spend tool does NOT cover

- **Same-user malware.** A program running as your Windows user can read Legion's memory (both secrets), click the native dialogs, rewrite the audit log together with its hashes, or call your wallet directly. Only a VM or a separate OS account stops that; what remains is whatever the wallet itself checks (a prompt or a spending grant, depending on the wallet).
- **The network is the wallet's own claim.** A P2PKH script is the same bytes on both networks, so the transaction does not say which network it is for. Legion rests on the wallet's fresh claim, the address version byte, the per-network allowlists and you reading the network word in the dialog. A program that answers on the wallet's port can claim `main`; it can only produce cards that you read, behind the switch, the arm, the allowlist and whatever the wallet checks.
- **Change outputs are wallet-claimed.** Legion holds no keys, so it cannot prove which output is change. One extra standard P2PKH output is accepted and shown; anything else is refused.
- **A reference lost in a crash.** If Legion stops between the build and the signing call, Legion's own code cannot abort it through the wallet's public interface, and the wallet's locked coins are released only by the wallet's own timeout.
- **A wallet that signs something other than the card** is caught only after the fact (freeze, mainnet off).
- **Approval fatigue** (two or three dialogs, plus whatever the wallet asks, which depends on the wallet) is limited by one arm per mainnet spend, tiny caps, a short card lifetime and a rate limit, not removed.
- **An agent's ordinary tools** (a shell, a web fetch) are outside all of this.
- **Whether and when the wallet asks depends on the wallet.** BRC-100 makes the `originator` a domain name and says nothing about local apps outside a browser; Legion's `legion.local` is self-declared, so any local program can claim it. In wallet-toolbox (`src/WalletPermissionsManager.ts`, read 2026-10-06), the code BSV Desktop builds on, `createAction` asks for a spending grant for the originator when the payment uses wallet funds, which in Legion's flow is step 4, BEFORE your card; spends inside a granted monthly amount do not ask again; `signAction` does not ask; a wallet setting can switch spending checks off. So treat Legion's last dialog as the per-spend gate. The wallet's own prompt is not always the last gate: its grant is a second check, which you keep one-time if the wallet offers that, or at or below Legion's caps. Not verified on a real wallet (checks W1 to W5).
- **The build step waits up to 15 minutes** (`createAction`, a safety cap; BRC-219 asks apps not to time out a wallet that is asking its user). Only if the wallet has not answered by then does Legion report `wallet-no-answer`; the Assayer is told to ask you to check the wallet instead of asking again. In that one case Legion's own code never received a reference, so it cannot release the build; decline it in the wallet. wallet-toolbox fails an unsigned build that stays unsigned for about 5 to 10 minutes (`TaskFailAbandoned` in ts-stack, check W3).
- **After Freeze or Disconnect, Legion's own code sends the wallet one kind of call only: `abortAction`**, to release an unsigned build it no longer wants (an open card, or a build the wallet finishes after you pressed Freeze, Disconnect or Cancel). It goes to the wallet address the build was asked of and can only release coins: Legion's own code never signs or sends with it (owner decision 2026-10-06).

## What it does NOT do

Legion's own code does no key handling (no keys or seed phrases anywhere), no signing and no broadcasting (the wallet signs and handles the broadcast), no balance or output reads, no standing or automatic spending, no scheduled spend, no spend from a run another bot, a room or an MCP client started, no paymail or public-key recipients and no more than one payment per request. The only wallet calls BSV mode can make are the four-question status probe and, inside the spend tool, three more (build without signing, sign, abort), all to a loopback address (and the app's own calls to its local core). The knowledge mode (`BsvNetwork`) is the literal `testnet`; spending has its own network rules (the wallet's own claim, pinned per request). Mainnet is built and OFF: the switch is off in a fresh install, the owner turns it on in the app, and each mainnet spend needs an Arm. An agent's ordinary tools (a shell, a web fetch) are outside all of this.

While BSV is off the Assayer is hidden everywhere and cannot be run: `/api/state` and the task routes (a task of the Assayer answers 404 like an id that never existed), the event stream (SSE), MCP (`legion_run`, `legion_continue`, `legion_vm`, `legion_status`, `legion_cancel`, `legion_recent_tasks`), the comms hub (`bot_list` omits it, `bot_send` to it says "Unknown bot" and creates nothing, a room it belongs to is dormant until it is back, and it cannot be added to a room), and the HTTP routes that start a task or drive its VM. A run of the Assayer that is waiting in the queue when you turn BSV off is cancelled (and the engine checks again when a queued job is about to start). Not hidden: the agent record by id (you can still edit or delete it in Settings), `GET /api/bsv` (it reports `assayerAvailable` for the toggle's own UI), and a run that was already in progress when you switched off, which finishes (its `bsv` notes are no longer readable to it).

### What the tripwire checks, and what it cannot

`test/bsv-tripwire.test.ts` and `test/bsv-review-tripwire.test.ts` (scanner: `test/bsv-scan.ts`) fail the build when ANY file under `src/` or `ui/src` (core, comms, kg, the UI, the electron shell and the stdio proxy) other than the two wallet files below contains `3321`, `WalletClient`, `HTTPWalletJSON`, `@bsv/sdk`, `createAction` or any wallet method name (`signAction`, `listOutputs`, `getPublicKey`, `internalizeAction`, `createSignature` and the rest of the BRC-100 list). The probe file may name only its four allowlisted harmless methods and is classed as a loopback-only HTTP client (it may not open a server, spawn a process or touch a non-loopback host). **The one spend file, `src/core/bsv/spend.ts`, may name exactly three wallet methods (`createAction`, `signAction`, `abortAction`) and register exactly one tool (`bsv_spend_request`), and only while its content hash matches the pin (`SPEND_PINS` in `test/bsv-scan.ts`, hash over the file with CRLF turned into LF; `.gitattributes` keeps it LF).** If the file differs from the pin it gets NO exemption, so the same edit fails every rule at once. The network table `src/core/bsv/networks.ts` is pinned the same way. In Legion's own code, every other rule keeps applying to `spend.ts`: no `fetch`, no node network or process module, no `eval`, no computed call, no network literal (it takes the network from the probe as an opaque value and looks everything up in the table), no policy setter (it may call only `evaluate`, `approve`, `deny`, `settle`, `resolveUnknown`, `status`, `snapshot`, `freeze`, `disarm`, `mainnetOff`, `voidPending` and `canSign`; it can only make Legion more careful, never arm, unfreeze or change a limit), and no wallet port in any source, `test/` and `scripts/` included (`test/bsv-port-guard.test.ts`). **To change either pinned file:** make the edit, get the reviewer's sign-off on the PR, run `node scripts/bsv-spend-pin.mjs` (it reads two local files and prints two hashes; no network, no writes), paste the new hashes into `SPEND_PINS`, and run the tripwire tests. A pin updated without the review defeats its purpose: the pin is a tripwire for unreviewed edits, not a proof that the reviewed code is right. It does not pin the files `spend.ts` imports (`policy.ts`, `audit.ts`, `wallet-probe.ts`); those stay under the other scans, the tests and the reviewer's checklist. Everywhere else the scan also fails on imports `@bsv/*`, uses `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` or an MCP client transport, imports a socket module (`https`, `http2`, `net`, `tls`, `dgram`, `dns`, `undici`, `axios`, `ws` and the like) or `child_process`, uses string decoding that can hide a name (`String.fromCharCode`, `atob`, base64), or registers a tool whose name is not a string literal or is wallet-shaped (a word such as `wallet`, `bsv`, `spend`, `pay`, `sign`, `broadcast`, `arm`, `freeze`). The only files allowed to do any of the network or process things are listed, each with its reason, in `ALLOWLIST` in `test/bsv-scan.ts`: the boat.dev client, the local HTTP/SSE/MCP server, the electron shell and the stdio proxy (both only talk to the core on 127.0.0.1), the UI's client of the local core, and the secret detector (decoding). A new file that needs one of these fails until someone adds it there, on purpose.

It spots names spelled in pieces (`'Wallet' + 'Client'`, `['Wallet','Client'].join('')`, `concat`, template parts, reversed strings, `replace` and `slice` of a literal, `\u0073` and `\x73` escapes), aliases of the network globals and computed access to them (`globalThis['fetch']`), and dynamic imports. Inside the BSV code (`src/core/bsv`, `ui/src/bsv`, `src/shared/bsv-*`, the Electron admin logic) it is stricter: a quoted identifier-shaped token that names signing, spending, broadcasting or inscribing is refused, as is a computed member built from pieces or a template, a computed call (`x[k]()`), `eval`, `Function`, `Reflect`, `this[...]` or `globalThis[...]`, and non-ASCII look-alike letters in code. No wallet port exists in any source: the probe has no default address, so `3321` is refused everywhere. It is a static scan, not a sandbox. It cannot stop a name assembled from data at run time, an `eval`, code in a dependency, or a shell command an agent runs through a tool it already has (the Assayer's Bash, or `legion_vm exec` in a VM): those are bounded by approvals, not by this test.

## Pack versioning

The pack has a `version` (now 8). The version is stored on the index node (`props.seedVersion`) and every seeded node carries `props.seedHash`, a hash of what the pack said: title, body, tags, confidence, type, scope, props (without the seed's own bookkeeping) and sources. The upgrade runs when you toggle BSV on, when you press **Load BSV pack**, and once at core start when BSV is already on (idempotent, logged, never blocks boot and never throws).

- Nothing loaded: every node is added.
- An older version loaded: missing nodes are added; nodes you never edited take the new text; nodes you edited (any of the fields above) are left alone and returned as `skippedEdited`; links that are missing are added, links that exist are never touched (your note or weight on a pack link stays). The toast and the API result say what happened (`loaded`, `upgraded`, `repaired`, `already-loaded`, and the counts).
- The same version loaded: nothing is rewritten, so a plain re-seed never touches your edits. A node that is simply missing is put back (`repaired`).
- Crash safety: nodes are written first, then links, and the index node (the version marker) last. A process that dies half way leaves an install that the next toggle, button press or start still upgrades.
- What you deleted stays deleted. Deleting a pack node, or a link between two pack nodes, or changing the relation of a pack link, is remembered (`seed-removed.json` beside the graph log); an upgrade does not bring it back and lists it as `skippedRemoved`. A node a human merged into another stays as the retired note it became: the upgrade neither rewrites nor revives it and lists it under `skippedEdited`.
- To take the pack text for a node, or to bring one back, ask for it by id: `POST /api/kg/seed/bsv {"restore":["bsv-tx-fees"]}` (BSV mode on). A deleted node comes back with its links; a node you edited is reset to the pack text. Unknown ids are refused (400) and nothing is written. Plain "delete the node and toggle again" does NOT bring it back: that is what the ledger is for.
- A node the new pack dropped is never deleted or archived: that is your call. A snapshot of the graph log is taken before anything is written.
- "Edited" means the current node no longer matches the stored `seedHash`. A node seeded with the first, narrower hash (title, body, tags, confidence) is compared on those fields only. An install from before hashes counts a node as untouched when it was never changed or still matches a text an earlier pack shipped (`seeds/bsv-legacy-hashes.json`). An archived or superseded pack node counts as edited.

## What the token split does and does not cover

Turning BSV mode on or off (`POST /api/bsv`) and every Library route need the admin secret that only the Legion app window holds, so reading `config.json` is no longer enough to flip the switch or accept its own notes. Every BSV policy change (the mainnet switch ON, arm, disarm, freeze, unfreeze, limits, allowlists) and every payment decision and resolution (the decision and resolve routes listed in docs/ARCHITECTURE.md) needs a second secret as well, the NATIVE secret: a second line on the core's stdin, held only by the Electron main process and never given to the window, an environment variable, argv, a log or a file. The core checks it in constant time and refuses with 403 without it, so neither the bearer token nor the admin secret that the window holds can switch mainnet on, arm, unfreeze, change limits, approve a payment or connect a wallet (the one thing the bearer token can do is Freeze, which only stops things), and a compromised page in the window cannot arm or unfreeze on its own: the request has to pass main's strict parser, its sender check (only the window's own page, not a navigated or foreign frame) and its native confirmation dialog. What this does NOT stop: a process running as your own user can still read Legion's memory (both secrets), edit its files, synthesize clicks on the native dialog, or call your BSV wallet directly on `127.0.0.1:3321`, which Legion cannot see. Only a VM or a separate OS account stops that, and what remains is whatever the wallet itself checks, which depends on the wallet. If the core was not started by the app (no native secret), policy changes are locked and the panel says so.

## Not built (design only)

Human-approved wallet reads (balances, outputs), reading a wallet's action list, a VM boundary for wallet tools, any spend by a run another bot, a room or an MCP client started, several outputs or paymail recipients in one request, typing the amount into a confirmation (a second dialog is used instead), an adversarial release gate run by an independent reviewer, and every real-wallet check in the Not verified section. The spend tool, the approval card, the native dialogs, the unknown-outcome rule and mainnet capability ARE built (the Spend section), tested against fake wallets only. The design, the threat model, what each safeguard blocks, the residual risks, the adversarial test plan and the exact questions for the owner are in `docs/BSV-WALLET-DESIGN.md`. The wallet choice plan is in the pack lesson `bsv-wallet-choice` (BSV Desktop first, HandCash BRC wallet beta second, BSV Browser later; never Yours/Panda, the old Metanet Desktop, bsv-mcp or any wallet that holds keys for Legion; keep any spending grant one-time if the wallet offers that, else at or below Legion's caps, and never auto-pay; Legion's own card is the per-spend gate and the wallet's grant a second check, in an order that depends on the wallet; originator `legion.local`; `@bsv/sdk` `WalletClient` only, not wallet-toolbox) and in the research note `bsv-wallets.md` kept with the project docs. The wallet choice is still a plan; the spend tool works with a wallet that answers the BRC-100 JSON interface on a loopback address, and which wallets Legion supports is the owner's decision.

## Not verified

Legion's code, tests, scripts and agents have never been pointed at the real BSV Desktop wallet on the owner's machine (it holds funds), and the spend tool has not been verified against any real wallet or with real funds. Tests use a fake loopback wallet on a random port (`test/bsv-fake-wallet.ts`; a guard test fails on the wallet port number anywhere in `test/` or `scripts/`), nothing that runs automatically may touch port 3321, and Legion itself contacts no wallet until the owner presses Connect. **What was seen by hand, once, read-only, on 2026-10-02** (the box in the Spend section): the real wallet's version string, network word, content type and absence of a prompt for the four status methods. **Still open, and only the owner's checks can settle them** (each is a row in `claude/tracker-pc-checks.md`; until a row is recorded, treat the matching statement as unverified):
- `U1`/`U2`: a real wallet honours "build without signing" and returns Atomic BEEF (or plain BEEF) that Legion's decoder reads (V1).
- `U3`: `abortAction` releases the locked coins (V2, V7).
- `U4`/`U13` (revised 2026-10-06): the first assumption, that the wallet asks at every `signAction` and keeps no standing grant for `legion.local`, does not hold for wallets built on wallet-toolbox (Residual risks). Now assumed: the wallet asks at least once, at `createAction`, for a spending grant, and you keep that grant one-time or at or below Legion's caps (W1 to W5, V5, V6, R6). A wallet that asks nothing at all for a first spend is a stop condition: Legion's dialogs would be the only gate, and R6 is to be aborted.
- `U6`: what the wallet sends back on a decline (treated as an unknown outcome; V8, V9, R9).
- `U7`/`U12`: the wallet's change is one standard P2PKH output (V1, V5).
- `U8`: the testnet network string and the address version bytes the wallet uses (V3). The mainnet word `mainnet` was seen (`U11`, V0).
- `U10`: the dialogs on a real desktop (ND1 to ND11); they were tested through a stub (`test/electron-emu`) that records the options main passes.
- `U14`: realistic fees against the per-network fee ceilings (V5, R4).
- Mainnet with real funds: R0 to R11, by the owner, by hand, a tiny amount, an own second address, never scripted, never by an agent.
- How a real wallet answers the status methods apart from the four seen, what its prompts say, and which origin rules apply (the origin is self-declared). The probe treats an unexpected answer as "network unknown", and the spend path refuses it.

## The interface

Static by design (a performance requirement, enforced by `test/bsv-ui-view.test.ts`): nothing in the BSV UI animates, and the only timers are the status poll (every 60 s, only while the window is visible and focused, and a re-render only when an answer changed) and the countdown (once a second, only while mainnet is armed and the window is visible and focused). Testnet: a calm cyan line along the title bar and a small text readout (`TESTNET`, and `block N` when a testnet wallet reported a height). Armed: a static amber frame around the window, an amber title-bar line, and a pill with the countdown, a **Freeze chain** button (also shown whenever a request is pending), **Disarm** and **Details**. A wallet on mainnet shows the warning pill without the amber frame. The BSV panel (the PANEL button next to the switch, the pill's Details, or the command palette) shows the wallet status with an address box, a Connect button (a native confirmation first) and, once connected, Disconnect and Check now, arming with a choice of duration, Freeze and Unfreeze, the limits, the mainnet switch (**Allow mainnet...** shows a warning dialog, **Switch mainnet off** acts at once), per-network limits and recipient allowlists (each change needs a native dialog), the requests waiting for your answer, unknown outcomes with a **Resolve** button (a native dialog), a Knowledge section that explains the BSV note count (the title bar shows `<n> BSV notes`, with `(pack 163)` when the number differs from the bundled pack, and `BSV notes: unknown` when it cannot be read) with a button that restores missing bundled notes, and the Activity list with the log's verification status and a Save log as file button. The panel does not show the amount, the address or the fee of a payment: those appear only in the native dialogs that the app words itself. There is also a tray item, Freeze BSV chain.

## BSV pack refresh

A human release step, never a runtime fetch: nothing in Legion downloads pack text. To refresh, re-read the primary sources, edit `seeds/bsv.json`, bump `version` (an unchanged version never rewrites existing nodes), and ship. Sources to re-check: the BSV Association docs hub (docs.bsvblockchain.org) and the BRC index (bsv.brc.dev), ts-stack (README, package manifests on npm: `@bsv/sdk`, `@bsv/wallet-toolbox`, `@bsv/simple`), the BSV Desktop repo and README (licence, ports, permissions), the HandCash BRC wallet docs, the Teranode repository and release notes (version, licence, networks), the Chronicle release page and node release notes (activation facts that are press-sourced), the ARC repository (bitcoin-sv/arc), and the 1Sat docs and SDK. Keep `props.verify` labels honest, keep controls that do not exist marked `built:false` and controls that exist in part marked `built:'partly'`, and run `npm test` (the seed tests refuse unmarked design claims, a design node without its `[Design]` title, unhedged claims of a control Legion does not have, and leftover Update/Correction paragraphs).
