# BSV mode: what it is today

BSV mode is an optional toggle in Settings, off by default, with the network fixed to testnet. This page is the plain truth about it; the pack lesson `bsv-status-today` says the same to the Assayer.

## What it holds

- The toggle (`src/core/bsv/`). Turning it on shows the Assayer bot, loads or upgrades the bundled knowledge pack in the Lattice scope `bsv` (also at core start when it is already on), and gives the Assayer a four-line preamble. Turning it off hides the Assayer and the scope again (the nodes are kept) and cancels the Assayer's queued runs.
- The Assayer: an advisory bot with no BSV tools. It explains, drafts and reviews. It is still an ordinary Legion agent: approval `ask` by default (you can change it, and `full` removes the prompts), VM off by default, and the normal Claude tools (shell, files, web fetch) behind that approval. Nothing in Legion signs or sends BSV and a human does every wallet step, in their own wallet; that is true of the code, not of the Assayer's good behaviour.
- The pack (`src/core/kg/seeds/bsv.json`, 157 nodes in 8 modules). Bots can read it. They cannot change its notes or its links, and cannot link onto it (`kg_link` to a `bsv` note is refused); only you can. The Assayer reads it with `kg_recall` and `scope: "bsv"`.
- `bsv-status-today`, `bsv-wallet-choice` and the safety lessons. Lessons about a later wallet phase are marked **`props.built:false`**, have a title that starts with **`[Design]`** (so a title in a related line or a briefing cannot read as fact), carry the `design` tag, start with "Design, not built in v0." and sit at confidence 0.6. The Assayer is told never to say those controls exist.

## What it does NOT do

No wallet, no keys or seed phrases, no signing, no broadcasting, no chain or wallet network call. No spend caps, no approval card for spends, no audit log, no Freeze, no mainnet (`BsvNetwork` is the literal `testnet`), no Legion-owned bsv tool.

While BSV is off the Assayer is hidden everywhere and cannot be run: `/api/state` and the task routes (a task of the Assayer answers 404 like an id that never existed), the event stream (SSE), MCP (`legion_run`, `legion_continue`, `legion_vm`, `legion_status`, `legion_cancel`, `legion_recent_tasks`), the comms hub (`bot_list` omits it, `bot_send` to it says "Unknown bot" and creates nothing, a room it belongs to is dormant until it is back, and it cannot be added to a room), and the HTTP routes that start a task or drive its VM. A run of the Assayer that is waiting in the queue when you turn BSV off is cancelled (and the engine checks again when a queued job is about to start). Not hidden: the agent record by id (you can still edit or delete it in Settings), `GET /api/bsv` (it reports `assayerAvailable` for the toggle's own UI), and a run that was already in progress when you switched off, which finishes (its `bsv` notes are no longer readable to it).

### What the tripwire guarantees, and what it cannot

`test/bsv-tripwire.test.ts` and `test/bsv-review-tripwire.test.ts` (scanner: `test/bsv-scan.ts`) fail the build when ANY file under `src/` or `ui/src` (core, comms, kg, the UI, the electron shell and the stdio proxy) contains `3321`, `WalletClient`, `HTTPWalletJSON`, `@bsv/sdk` or `createAction`, imports `@bsv/*`, uses `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource` or an MCP client transport, imports a socket module (`https`, `http2`, `net`, `tls`, `dgram`, `dns`, `undici`, `axios`, `ws` and the like) or `child_process`, uses string decoding that can hide a name (`String.fromCharCode`, `atob`, base64), or registers a tool whose name is not a string literal or is wallet-shaped (a word such as `wallet`, `bsv`, `spend`, `pay`, `sign`, `broadcast`, `arm`, `freeze`). The only files allowed to do any of the network or process things are listed, each with its reason, in `ALLOWLIST` in `test/bsv-scan.ts`: the boat.dev client, the local HTTP/SSE/MCP server, the electron shell and the stdio proxy (both only talk to the core on 127.0.0.1), the UI's client of the local core, and the secret detector (decoding). A new file that needs one of these fails until someone adds it there, on purpose.

It spots names spelled in pieces (`'Wallet' + 'Client'`, `['Wallet','Client'].join('')`, template parts), aliases of the network globals and computed access to them (`globalThis['fetch']`), and dynamic imports. It is a static scan, not a sandbox. It cannot stop a name assembled from data at run time, an `eval`, code in a dependency, or a shell command an agent runs through a tool it already has (the Assayer's Bash, or `legion_vm exec` in a VM): those are bounded by approvals, not by this test.

## Pack versioning

The pack has a `version` (now 3). The version is stored on the index node (`props.seedVersion`) and every seeded node carries `props.seedHash`, a hash of what the pack said: title, body, tags, confidence, type, scope, props (without the seed's own bookkeeping) and sources. The upgrade runs when you toggle BSV on, when you press **Load BSV pack**, and once at core start when BSV is already on (idempotent, logged, never blocks boot and never throws).

- Nothing loaded: every node is added.
- An older version loaded: missing nodes are added; nodes you never edited take the new text; nodes you edited (any of the fields above) are left alone and returned as `skippedEdited`; links that are missing are added, links that exist are never touched (your note or weight on a pack link stays). The toast and the API result say what happened (`loaded`, `upgraded`, `repaired`, `already-loaded`, and the counts).
- The same version loaded: nothing is rewritten, so a plain re-seed never touches your edits. A node that is simply missing is put back (`repaired`).
- Crash safety: nodes are written first, then links, and the index node (the version marker) last. A process that dies half way leaves an install that the next toggle, button press or start still upgrades.
- What you deleted stays deleted. Deleting a pack node, or a link between two pack nodes, or changing the relation of a pack link, is remembered (`seed-removed.json` beside the graph log); an upgrade does not bring it back and lists it as `skippedRemoved`. A node a human merged into another stays as the retired note it became: the upgrade neither rewrites nor revives it and lists it under `skippedEdited`.
- To take the pack text for a node, or to bring one back, ask for it by id: `POST /api/kg/seed/bsv {"restore":["bsv-tx-fees"]}` (BSV mode on). A deleted node comes back with its links; a node you edited is reset to the pack text. Unknown ids are refused (400) and nothing is written. Plain "delete the node and toggle again" does NOT bring it back: that is what the ledger is for.
- A node the new pack dropped is never deleted or archived: that is your call. A snapshot of the graph log is taken before anything is written.
- "Edited" means the current node no longer matches the stored `seedHash`. A node seeded with the first, narrower hash (title, body, tags, confidence) is compared on those fields only. An install from before hashes counts a node as untouched when it was never changed or still matches a text an earlier pack shipped (`seeds/bsv-legacy-hashes.json`). An archived or superseded pack node counts as edited.

## Not built (design only)

Spend tool, spend caps, approval broker for spends, audit log and Freeze, native mainnet arming, VM boundary for wallet tools, the Legion-owned bsv tool, the wallet connection itself. The plan is in the pack lesson `bsv-wallet-choice` (BSV Desktop first, HandCash BRC wallet beta second, BSV Browser later; never Yours/Panda, the old Metanet Desktop, bsv-mcp or any wallet that holds keys for Legion; never grant a monthly limit or auto-pay; two-stage approval, Legion's card then the wallet's own prompt; originator `legion.local`; `@bsv/sdk` `WalletClient` only, not wallet-toolbox) and in the research note `bsv-wallets.md` kept with the project docs. None of it ships until you have reviewed the wallet phase.

## BSV pack refresh

A human release step, never a runtime fetch: nothing in Legion downloads pack text. To refresh, re-read the primary sources, edit `seeds/bsv.json`, bump `version` (an unchanged version never rewrites existing nodes), and ship. Sources to re-check: the BSV Association docs hub (docs.bsvblockchain.org) and the BRC index (bsv.brc.dev), ts-stack (README, package manifests on npm: `@bsv/sdk`, `@bsv/wallet-toolbox`, `@bsv/simple`), the BSV Desktop repo and README (licence, ports, permissions), the HandCash BRC wallet docs, the Teranode repository and release notes (version, licence, networks), the Chronicle release page and node release notes (activation facts that are press-sourced), the ARC repository (bitcoin-sv/arc), and the 1Sat docs and SDK. Keep `props.verify` labels honest, keep controls that do not exist marked `built:false`, and run `npm test` (the seed tests refuse unmarked design claims, a design node without its `[Design]` title, unhedged claims of a control Legion does not have, and leftover Update/Correction paragraphs).
